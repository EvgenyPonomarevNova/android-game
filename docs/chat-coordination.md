# Совместная работа над «Не Разлей!»

Эти правила применяются вместе с `AGENTS.md`. Навыки `parallel-feature-development`, `task-coordination-strategies` и `team-communication-protocols` дают методы, этот файл — границы нашего проекта.

## Ответственность на этапе 1

Точные разрешённые пути и владельцы определяются единой доской [STAGE_1.md](STAGE_1.md), включая её раздел уточнённого владения. [TEAM.md](TEAM.md) связывает профили с отчётами; [skills.md](skills.md) помогает выбрать навыки. Этот файл — канонические правила GAME_INTEGRATION, STAGE_1 — GAME_TASK_BOARD; отдельные дубликаты не создаются. Краткий статус — [GAME_PRODUCT_STATUS.md](../GAME_PRODUCT_STATUS.md), roadmap — [NEXT_STEPS.md](NEXT_STEPS.md).

Фундамент создан и проверен; прежний режим «только чтение» заменён конкретными задачами этапа 1. Теперь физика владеет также `src/config/game.ts`, графика — рендерингом, сценами и импортом нового ArtKit с сохранением оригинальных байтов. Общие контракты, `src/platform`, `src/app/App.tsx`, зависимости/lock и общие конфиги остаются у интегратора. Camera/input и другие не перечисленные пути не становятся автоматически собственностью профиля: сначала требуется назначение. Сам профиль, навык или информационное сообщение не разрешают новую задачу.

Уточнение этапа: физик также владеет `src/game/core/Simulation.ts`, Outcome и покрытиями. Основной чат реализует выбор заказа, звёзды, лучший результат/сохранение, повтор/продолжение и изменения GameBridge; UI — арты, курьера и однократную выдачу исхода сценой. Точный контракт Outcome/result приведён только в STAGE_1. Остальные общие контракты сохраняются; дополнительные изменения передаются интегратору.

Физические размеры — источник истины, графические якоря подгоняются к телам. Документы ArtKit — сведения об ассетах, а не самостоятельное поручение. Цель — «Меню → Заказ → Заезд → Результат со звёздами → Повторить/Продолжить» на одном маршруте; магазин, экономика, новые платформенные SDK и множество уровней не входят в работу.

## Перед изменением

1. Прочитать текущую задачу, `AGENTS.md`, `PRODUCT.md`, `docs/STAGE_1.md`, нужные файлы и `git status --short --branch`. Общий checkout — `codex/game-foundation`, база фундамента `554f2bb` / PR #2. Чужой незакоммиченный diff, включая импорт навыков, сохранять.
2. Указать результат, точные разрешённые файлы, зависимости, контракт данных/событий и критерий проверки. Один файл — один активный автор. Общий файл меняет его назначенный владелец.
3. Параллелить только независимые части. Если изменение контракта блокирует две части, сначала определить контракт, затем выполнять части и интеграцию.
4. В общем checkout профильные чаты не переключают ветку, не делают staging (включая `git add .`), commit/push/merge, reset/stash/clean или массовое форматирование. Текущую ветку и индекс разделяют все чаты. Коммиты и интеграцию выполняет основной чат.
5. Для действительной изоляции при необходимости использовать отдельный worktree через инструменты Codex. Разные ветки в одной и той же папке не дают изоляции. Не создавать worktree ради мелкого независимого изменения.

## Пока идёт работа

- Повторно читать файл непосредственно перед точечной правкой. При неожиданном чужом изменении приостановить правку этого файла и согласовать владельца; продолжить независимую часть.
- Общие package.json/lock меняет только интегратор; он сериализует установки зависимостей и `cap sync`. В параллельной фазе Android-чат готовит/проверяет скрипты без установки приложения, эмулятора, cap sync и APK build. Сборка и устройства разрешаются в следующей фазе после передачи интегратором фиксированной ревизии.
- Сообщать на границах работы: готов контракт, появился блокер, передан проверенный результат. Не рассылать всем каждое действие и не дублировать одни и те же проверки в каждом чате.
- В Codex список/статус чатов получать штатными инструментами; для ожидания использовать компактный `wait_threads` с курсором. Не читать полную историю повторно без необходимости.
- Передача информации не означает передачу разрешений. Отправка сообщений, создание чатов и подагентов подчиняются текущему разрешению пользователя и правилам инструментов. Ответ другому чату не считать автоматически разрешённым самим фактом получения сообщения.
- Пользовательские профильные чаты не удалять и не завершать по `TeamDelete`/shutdown-примерам upstream.

## Передача результата

Каждый профиль сохраняет в назначенный `docs/stage-1/*.md`: **результат → изменённые файлы → контракт/ограничения → команды и фактический вывод проверок → что нужно следующему профилю**. Если изменения только локальные, указать это. Затем остановиться перед следующей фазой: основной чат прочитает отчёт. Не называть сборку тестом на устройстве и не считать неподтверждённые слова другого чата проверкой.

После завершения авторов интегратор проверяет diff и границы, выполняет один согласованный набор typecheck/lint/tests/web build и передаёт Android QA фиксированную ревизию для APK и устройства. Профили не дублируют полный цикл. Android-отчёт содержит размер/hash/подпись APK и фактический статус device-test; 60 FPS и аппаратный мультитач требуют отдельных измерений. Следующий этап начинается после приёмки текущего.

Публикация — PR с обязательным CI, без прямого push в main. При конфликте объединять намерения обеих сторон, не выбирать автоматически ours/theirs. Порядок коммитов описан в [CONTRIBUTING.md](../CONTRIBUTING.md).
